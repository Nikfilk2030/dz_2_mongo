## Данные

Позиции встроены в заказ, потому что читаются вместе. История хранится отдельными заказами, чтобы документ покупателя не рос без ограничения. цену фиксируем на момент покупки очевидно

Валидатор `strict/error` проверяет уникальность размеров и дефолтные числовые валидации

`elemMatch` делает правильно эту самую гадскую mongo проверку, когда вы делаете:

> Есть размер L? Да

## Индекс

> Историю мы уже умеем получать. Как сделать, чтобы базе не приходилось просматривать все заказы ради последних двадцати?

`{userId: 1, status: 1, createdAt: -1, _id: 1}`: сначала равенства, потом сортировка. `hint` не использовал.

На 10000 заказов для `userId: 2500`, `status: 'paid'`:

| Вариант | nReturned | totalKeysExamined | totalDocsExamined | Отдельная SORT |
|---|---:|---:|---:|---|
| До индекса | 20 | 0 | 10000 | Да |
| После | 20 | 20 | 20 | Нет |

Вместо `COLLSCAN` и `SORT` появился `IXSCAN` (индекс скан) без отдельной сортировки. Состав и порядок заказов совпали

## Смена primary

Один клиент до и после stepDown. Записи с `{w: 'majority', j: true, wtimeout: 10000}`. Старый документ прочитан, новая запись подтверждена. Клиент отслеживает роли по списку узлов и имени replica set, вручную URI не меняется. Majority не гарантирует, что любая secondary уже применила запись, поэтому она может вернуть старые данные

## Шардирование

`userId: 2500` попадает в диапазон B, запрос идёт только туда. Для `status: 'paid'` нужны A и B, поскольку нет ограничения по `userId`.

Индекс по `status` может ускорить поиск внутри шардов, но не меняет распределение по `userId` и число опрашиваемых шардов.
